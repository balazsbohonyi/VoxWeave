## Summary

The root cause is a single-entry Vite build. Currently `vite.config.ts` has no `build.rollupOptions.input`, so Vite defaults to a single-page build that only produces `dist/index.html`. In dev mode, Vite serves all four HTML files from the project root via its dev server directly, so all windows work. In production, `frontendDist` = `dist/` contains only one HTML file (the settings page), and every window URL — `indicator.html`, `toast.html`, `wizard.html` — resolves to `dist/index.html` (settings). All three B002 symptoms stem from this single root cause.

The fix is mechanical: move all four HTML files into `src/`, configure Vite's `build.rollupOptions.input` to produce four HTML outputs in dist, and update `tauri.conf.json` window `url` fields to match. No Rust code changes, no frontend component changes, no new dependencies.

Vite's output path mirrors the input file's location relative to the project root. Files placed at `src/*.html` will be emitted as `dist/src/*.html`. Tauri window URLs (relative to `frontendDist`) must therefore be `src/index.html`, `src/settings.html`, etc.

**Primary recommendation:** Add `rollupOptions.input` with `path.resolve` for all 4 HTML files, move files to `src/`, update `tauri.conf.json` — three edits, no new dependencies.

## Architecture Patterns

### Vite Multi-Page Configuration
**What:** Declare multiple HTML entry points via `build.rollupOptions.input`. Each entry is processed independently and produces its own HTML, CSS, and JS chunks in dist.

**When to use:** Any Tauri or web project with multiple distinct windows/pages that must each bootstrap a different Vue app instance.

**Official pattern** (from vite.dev/guide/build#multi-page-app):
```typescript
// vite.config.ts
import { resolve } from "node:path";
import { defineConfig } from "vite";
import vue from "@vitejs/plugin-vue";
import tailwindcss from "@tailwindcss/vite";

const host = process.env.TAURI_DEV_HOST;

export default defineConfig(async () => ({
  plugins: [vue(), tailwindcss()],
  clearScreen: false,
  build: {
    rollupOptions: {
      input: {
        indicator: resolve(__dirname, "src/index.html"),
        settings: resolve(__dirname, "src/settings.html"),
        wizard: resolve(__dirname, "src/wizard.html"),
        toast: resolve(__dirname, "src/toast.html"),
      },
    },
  },
  server: {
    port: 1420,
    strictPort: true,
    host: host || false,
    hmr: host
      ? { protocol: "ws", host, port: 1421 }
      : undefined,
    watch: {
      ignored: ["**/src-tauri/**"],
    },
  },
}));
```

Key detail: Vite **ignores the input key names** (`indicator`, `settings`, etc.) when determining output paths. It uses the **resolved file path** relative to the project root. `src/index.html` → `dist/src/index.html`, `src/settings.html` → `dist/src/settings.html`.

### Tauri Window URL Updates
Tauri window `url` fields are resolved relative to `frontendDist` (`../dist` from tauri.conf.json's perspective, i.e., `dist/`). With HTML files now at `dist/src/*.html`, the URLs become:

```json
// tauri.conf.json — updated window url fields
{ "label": "settings",   "url": "src/settings.html" }
{ "label": "indicator",  "url": "src/index.html"     }
{ "label": "toast",      "url": "src/toast.html"     }
{ "label": "wizard",     "url": "src/wizard.html"    }
```

### HTML Script Src Attributes — No Change Needed
Current HTML files use root-relative paths:
```html
<script type="module" src="/src/windows/indicator/main.ts"></script>
```
Vite rewrites these to hashed asset paths at build time (`/assets/index-XYZ.js`). Moving the HTML file's location does not affect how Vite resolves and rewrites these imports. **No content changes to any HTML file.**

### Anti-Patterns to Avoid
- **Keeping HTML files in project root with rollupOptions.input:** Vite would produce `dist/index.html` for settings, colliding with `dist/src/index.html` for indicator — ambiguous and error-prone.
- **Using string paths without `resolve()`:** Relative string paths in `rollupOptions.input` are resolved from CWD, which may differ. Use `resolve(__dirname, ...)` or `resolve(import.meta.dirname, ...)` for reliability.
- **Forgetting to delete old HTML files from project root:** Old root-level HTML files are not processed by Vite's multi-page build (they're not in `input`), but leaving them is confusing. Delete them.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Multi-page output | Custom copy scripts, post-build scripts | `build.rollupOptions.input` | Vite handles hashing, chunk splitting, CSS extraction per entry |
| Path resolution | String concatenation | `resolve(__dirname, ...)` | Platform-safe, relative to config file not CWD |

## Common Pitfalls

### Pitfall 1: import.meta.dirname vs __dirname
**What goes wrong:** `import.meta.dirname` is only available in ESM contexts. If `vite.config.ts` doesn't have `"type": "module"` in package.json, it may not be available.
**Why it happens:** Node.js ESM/CJS distinction.
**How to avoid:** Use `resolve(__dirname, ...)` — `__dirname` is always available in Vite config files regardless of module type, because Vite processes the config file in a compatible way. Both work in this project (package.json has `"type": "module"` confirmed by existing comment in vite.config.ts).
**Warning signs:** `TypeError: Cannot read properties of undefined (reading 'dirname')` at Vite startup.

### Pitfall 2: Vite dev server not serving new `src/*.html` paths
**What goes wrong:** After moving files to `src/`, the Tauri dev URL `http://localhost:1420` still routes windows by their tauri.conf.json `url` field — but in dev mode Tauri uses `devUrl` (the Vite dev server), not the built HTML files. The Vite dev server serves files relative to project root by default.
**Why it happens:** In dev mode, window URLs like `src/index.html` are resolved against the Vite dev server root. Vite serves `src/index.html` directly by filesystem path — this works because Vite's dev server serves static files from the project root.
**How to avoid:** No special handling needed. Vite dev server serves any file under its root (the project directory) by path. `http://localhost:1420/src/index.html` resolves correctly.
**Warning signs:** 404 errors when opening windows in dev mode after the change.

### Pitfall 3: Tauri URL path format (leading slash vs relative)
**What goes wrong:** Using `/src/settings.html` (with leading slash) in `tauri.conf.json` `url` field when Tauri expects a relative path from `frontendDist`.
**Why it happens:** Confusing filesystem paths with URL paths.
**How to avoid:** In production, Tauri resolves window `url` relative to `frontendDist`. Use bare relative paths: `src/settings.html`, not `/src/settings.html`. In dev mode, Tauri prepends `devUrl` to the path, making it `http://localhost:1420/src/settings.html` — also correct.
**Warning signs:** Window fails to load in production build (blank window or 404 in Tauri's custom protocol).

### Pitfall 4: Assets referencing wrong base path
**What goes wrong:** CSS/JS assets emitted by Vite use `/assets/...` paths. If Tauri's custom protocol resolves assets relative to the HTML file's location (`dist/src/`), the `/assets/` path must still resolve correctly.
**Why it happens:** Multi-page builds with HTML files in subdirectories can break asset base URL assumptions.
**How to avoid:** Vite's default `base: "/"` emits assets with absolute paths like `/assets/index-hash.js`. Tauri's custom protocol (`tauri://localhost`) serves all files from the `frontendDist` root, so `/assets/...` resolves to `dist/assets/...` regardless of which HTML file is loaded. No `base` config change is needed.
**Warning signs:** Console errors about failed asset loads (404 for `/assets/*.js` or `.css`) in production.
